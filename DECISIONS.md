# DECISIONS

Every choice made without asking the owner, with the reason. Newest at the bottom. Change any of these by editing the code/config named in the entry.

| # | Topic | Decision | Why |

| D1 | REA / inDrive APK | First build: no APK was available, so flows were designed from the brief and general ride-hailing patterns. 2026-10-28: the owner supplied inDrive 5.190.0 (APKMirror bundle, signature checked) and a static flow study was done: manifest, class names and string resources only, never installed or run, nothing copied. Findings and a gap list with priorities are in `spec/REA.md`. The APK itself is not kept in the repo. | Section 6 of the brief; learning flows without copying code, text, assets or APIs. |
| D2 | Repo layout | Monorepo: `backend/` (Node+TS), `admin/` (React+Vite), `apps/rider`, `apps/driver` (Flutter), `packages/ridema_core` (shared Flutter code), `infra/` (Compose, Caddy, OSRM, backups). | One place, shared contracts, one CI. |
| D3 | Backend framework | Fastify 5 + TypeScript, raw SQL with `pg` and plain SQL migration files, `zod` for validation, `vitest` for tests. | Fast, small, no ORM magic around the race-sensitive SQL (conditional updates, partial unique indexes). |
| D4 | Password hashing | Argon2id via `@node-rs/argon2` (prebuilt binaries). | OWASP recommendation, no native toolchain needed. |
| D5 | Tokens | Access token: JWT (HS256), 15 min. Refresh token: opaque 256-bit, 30 days, stored hashed, rotated on every use; reuse of a rotated token revokes the whole family. | Section 3. |
| D6 | Email verification | 6-digit code **and** a link carrying a signed token, both valid 30 min. | Code is easier on phones; link is easier on desktop. |
| D7 | Phone verification | WhatsApp OTP once per user. After a phone is verified it can only be changed through a data-correction request handled by an admin. Max 3 codes per number per day, 5 wrong tries per code. | "Used only ONCE per user". |
| D8 | Brand | Name `RideMA` in `packages/ridema_core/lib/brand.dart` (`kAppName`) + `assets/brand/`. Colours: primary emerald `#0B6E4F`, accent saffron `#F4A300`, ink `#1D1D1F`. Logo: our own simple wordmark (SVG). | Clearly distinct from inDrive's palette; easy to rename. |
| D9 | Minimum offer | Rider offer must be ≥ city `min_fare` and ≥ 70 % of the suggested price; counter-offers must be between the rider offer and 300 % of the suggested price. All percentages per city. | Stops spam offers while keeping bargaining. |
| D10 | "5 best" offers | Rank: lowest price, then shortest pickup ETA, then highest rating. Rider sees the top 5 active offers; others stay queued and move up when one expires. | Simple, explainable. |
| D11 | Rider cancellations | Free (no penalty) before the driver taps "I've arrived". Every rider cancellation of an accepted ride is counted; at 3 in a rolling 7 days the app shows a warning. No block for riders. | Section 2. |
| D12 | Driver cancellations | Each cancel after accepting = 1 penalty point (shown rating = average − 0.05 × points from the last 30 days, floor 1.0). 3 cancels in 24 h → blocked 2 h; 5 in 7 days → blocked 24 h. Driver may cancel without penalty as "rider no-show" 5 min after arriving. All numbers per city. | Section 2. |
| D13 | Subscription rule | When `subscriptions_enabled` is on: every driver gets 10 completed rides per day free. To bid on an 11th ride in the same day a driver needs an active 99 DH/30-day subscription. Default OFF. | Simplest reading of "99 DH/month for drivers above 10 rides/day". |
| D14 | Payment provider | `PaymentProvider` interface with `cashplus`, `wafacash`, `card`, `wallet` adapters. Without merchant keys they run in mock mode: they create a reference code and an admin marks it paid. The platform never holds money. | No merchant contracts yet. |
| D15 | Ride states | `searching → accepted → arrived → in_progress → completed`; terminal `cancelled`, `expired`. | Short, matches the bidding product. |
| D16 | Pickup PIN | 4 digits generated at acceptance, shown to the rider, typed by the driver to start the trip. Feature flag `pickup_pin` (default ON). | Section 5 safety. |
| D17 | Voice calls | WebRTC audio, signalling through our Socket.IO server, TURN by a `coturn` container. Only the two parties of an active ride can call; phone numbers are never sent to the other party. | No third-party telephony account needed; numbers stay private. |
| D18 | Public map pages (trip share, admin live map) | Leaflet + OpenStreetMap tiles with attribution. Google Maps SDK is used inside the mobile apps only. | No Google Maps JavaScript key in the requested key list; share pages are low traffic. |
| D19 | Router fallback | `RouterProvider` has an `osrm` adapter and a `haversine` fallback (straight line × 1.3, 25 km/h) used in tests and when OSRM is down. | OSRM data could not be downloaded in the build container. |
| D20 | Retention defaults | GPS route points 12 months; rides + ride events 5 years; SOS 2 years; rejected-driver documents 6 months after rejection; approved-driver documents until 6 months after account deletion or driver exit; verification codes 7 days; expired refresh tokens 30 days; idempotency keys 48 h; admin audit log 5 years; consent log kept for account life + 5 years; outbox processed rows 7 days. All editable in admin settings. | Law 09-08 asks for limited, declared periods; 5 years covers civil/commercial disputes. |
| D21 | Account deletion | Deletion removes personal data immediately (name, email, phone, documents, tokens, devices, push tokens, route points). Ride rows are kept for the retention period with the user replaced by an anonymous placeholder so the other party's history and receipts stay valid. | "Fully deletes" personal data while keeping legally needed trip records non-identifying. |
| D22 | CIN storage | Only the last 4 characters of the CIN number are stored in clear (`cin_last4`). Full ID images are stored encrypted (AES-256-GCM, per-file data key wrapped by a master key from env). | Section 5. |
| D23 | Admin access | Admins log in with email + password + **mandatory TOTP**. Admin API routes check `ADMIN_IP_ALLOWLIST` (CIDR list, empty = allow all, logged at boot as a warning). Caddy also restricts `/admin`. | Section 5. |
| D24 | Idempotency | All POST/PUT/PATCH/DELETE under `/v1` require an `Idempotency-Key` header (UUID). Same key + same body replays the stored response; same key + different body → 422. | Section 5. |
| D25 | Outbox | Business writes insert `outbox` rows inside the same transaction. A dispatcher (LISTEN/NOTIFY + 1 s poll) delivers to Socket.IO, FCM and email after commit. | Section 5. |
| D26 | Flutter state management | `provider` + `ChangeNotifier`, `dio` for HTTP, `socket_io_client`, `flutter_foreground_task` for the driver foreground service. | Small, well-known packages. |
| D27 | Remote config | Apps read `api_base_url` from Firebase Remote Config; if Firebase is not configured or unreachable they use the compiled default (`https://<SERVER_IP>.sslip.io`) and the last value cached on the phone. | Section 4; lets us move domain without an app update. |
| D28 | Admin panel stack | React 18 + Vite + TypeScript + react-router, plain fetch client, vitest + Testing Library. | Section 1. |
| D29 | Languages | ARB files for ar/fr/en in `ridema_core`. Default locale = phone locale if ar/fr/en, else French. | Morocco; French is the safest fallback. |
| D30 | Driver types | Stored per city as `enabled_driver_types`. Meknes: `taxi`, `licensed_operator` on; `private_car` off. Riders don't choose a type; all enabled types receive requests. | Section 2. |
| D31 | Car rules | Validated at onboarding and re-checked at approval: model year ≥ current year − 6 (under 7 years), 4 doors, A/C = yes. Per-city overridable. | Section 2. |
| D32 | Licence age | Licence issue date must be ≥ 3 years before the application date. | Section 2. |

Backups are encrypted client-side with libsodium using `BACKUP_ENCRYPTION_KEY` (base64, 32 bytes). | github.com and Debian mirrors are blocked in the build container; a static binary avoids glibc mismatches. While `BACKUP_STORAGE_BUCKET` is empty the archive command drops WAL (exit 0) so the disk can't fill. | Simple loop instead of cron; safe before backup storage exists (B7). |
| D35 | Infra details | Compose is run from the repo root with `--env-file .env` (deploy links `infra/.env`); `RIDEMA_ENV_FILE` lets `infra/test.env` stand in for checks. | D37 | Admin panel details | Hash router (`/admin/#/…`, matches the SOS e-mail link `#/sos/:id`); access token in memory, refresh token in `sessionStorage` (closing the tab ends the session); one fetch client refreshes once on `401 TOKEN_INVALID` and retries with the same `Idempotency-Key`, and also retries a write once with the same key after a network error; UI strings in `admin/src/dict.ts` (French default, English toggle remembered in `localStorage`); brand name from `admin/src/brand.ts`. Live updates go socket → in-app bus → pages; the live map also polls `GET /v1/admin/live` every 10 s. SOS sound is a WebAudio beep (no audio file). Decrypted documents are fetched with the bearer token, never by URL: images shown as `data:` URLs (allowed by the Caddy CSP), PDFs as a `blob:` URL in an iframe plus an "open in a new tab" link. `admin/dist` is a build output (gitignored): run `npm ci && npm run build` in `admin/` before Caddy serves it. | Fewest moving parts; keeps tokens out of URLs and long-lived storage; works under the existing CSP. |
| D38 | Shared Flutter package | `packages/ridema_core` exposes one import. Apps start with `RideMaApp(app:, homeBuilder:)` (boot → app config/force update → language picker → Welcome or home) and use `CoreServices.of(context)` (`api`, `realtime`, `auth`, `boot`, `location`, …). Firebase push/Crashlytics/Remote Config are thin wrappers that become no-ops when `Firebase.initializeApp()` fails. | One place for shared flows; works as a plain path dependency with no build step in the apps. |
| D39 | App HTTP retries | `ApiClient` retries a call at most 2× after a network error/timeout, only for GETs and for writes that carry an `Idempotency-Key` (same key on every retry, and on the retry after a token refresh). The three key-exempt writes (location, estimate, SOS location) are never auto-retried. Device id = UUID v4 in shared_preferences; tokens in flutter_secure_storage. | Safe replays thanks to D24; location pings are frequent so a lost one is simply replaced. |
| D40 | Account/app role mismatch and signup login | A rider account logging into the driver app (or the reverse) is refused client-side with `WRONG_ROLE` and the new session is logged out. After email verification the app logs in automatically with the password typed at signup (kept in memory only, never stored). | One role per account (SPEC §2); fewer steps for new users. |
| D41 | SOS and calls in the apps | SOS: the alert `POST` starts first, the dialer opens immediately with the number from `emergency_numbers` (no waiting on the network); location is re-sent every 10 s only while the SOS sheet is open. Voice calls: callee opens the mic and answers `call:accept`, caller then sends the SDP offer; ICE candidates received before the remote description are queued; ring timeout 45 s; a second invite during a call is auto-rejected. | An emergency call must never wait for the API; simple, deterministic signalling. |
| D42 | App platform channels | `ma.ridema/apk_installer` (`canInstall`, `openInstallSettings`, `install {path}`; the APK is downloaded by Dart into `cache/updates/`) and `ma.ridema/device_integrity` (`isRooted`, `isMockLocation {lat,lng,mocked}`, `playIntegrityToken {nonce}`) are implemented on the Android side by the apps; missing channels fall back to safe defaults. | D44 | Driver location rhythm and background | While online or on a ride the app sends a fix when ≥ 4 s passed AND the car moved ≥ 15 m, plus a heartbeat every 30 s when parked (`LocationThrottle`). Socket `driver:location` first, REST `POST /v1/driver/location` only when the socket is down or the ack times out. The UI isolate streams the location; the `flutter_foreground_task` service (type `location`, notification channel `online_status`, `stopWithTask=false`) keeps the process alive and, if the UI isolate stops beating for 25 s (app swiped away), posts the location over REST every 15 s with the last access token until it expires, then its notification asks the driver to reopen the app. Going online needs location "while in use" at least; "all the time" is asked right after the disclosure and only recommended (a snack explains) because the location FGS keeps working with while-in-use. `apps/driver/lib/src/controller/`. | SPEC asks ~4 s / 15 m; the server keeps route points ≥ 3 s / 10 m and rate-limits 30 fixes / 10 s. Refreshing tokens from the service isolate would race the UI's rotating refresh token (D5), so the backup only uses the current access token. |
| D45 | Driver device checks | Client blocks going online on fake GPS (`Position.isMocked`, recent `Location.isMock`/`isFromMockProvider` fixes, a mock-location app allowed in AppOps among visible packages, legacy setting) and on root (su paths, test-keys, Magisk/KernelSU traces and packages, writable system mounts, `which su`), shows the Device check screen and reports the verdict with `POST /v1/me/devices`; the server is not asked to go online in that case. A mocked fix while online forces offline. No `QUERY_ALL_PACKAGES`: known root/fake-GPS packages are declared in `<queries>`. Play Integrity Standard token (project number from `PLAY_INTEGRITY_PROJECT_NUMBER`; none → no token). Integration tests on emulators (rooted images) replace only the root check. | Server flags (`mock_location_block`, `root_block`) could be off in a city; the client is stricter so a faked position never reaches riders. Play policy discourages QUERY_ALL_PACKAGES. |

The battery guide opens once after the first successful go-online and from the menu. Without `MAPS_ENABLED=true` a drawn placeholder map is used. | Familiar driver flows with our own layout and words; keeps the app usable without a Maps key. |

"No driver found" offers raise-and-retry, same-fare retry or Home. The rating screen shows the cash fare first; Skip is allowed. `apps/rider/lib/src/ui/`. | Familiar ride-hailing layout with our own brand and copy; RTL mirroring is the platform convention. |

The disclosure is auto-shown once (pref `rider.location_asked`); afterwards a banner offers "Allow location". Same for the notifications explainer. | Never block the rider when keys or permissions are missing. |
| D50 | Rider restore of finished rides | The rider app stores the id of its last ride (`rider.last_ride_id`). | D51 | Rider contacts for trip share | "From my contacts" uses the system picker of `flutter_contacts`; Android needs `READ_CONTACTS` to read the picked number, so it is declared and requested only on that tap; typing name + phone needs no permission. | D56 | Reverse geocoding (pickup address) without a paid API | `GET /v1/geo/reverse` builds the pickup line from three free sources: the street name of the nearest road in our own OSRM graph (`/nearest`, kept only when named and ≤ 60 m away), the nearest built-in landmark (≤ 700 m; at ≤ 80 m the landmark itself is the address), and the service city. Labels: `Street, near Landmark` / `Landmark` / `Street, City` / `near Landmark` / `City`, in ar/fr/en (landmark and city names translated; street names as in OpenStreetMap). Cached in Redis 7 days per ~11 m cell (4 decimals) and language; answers without a street are not cached while OSRM is the router so a warming OSRM doesn't pin them. The rider app uses Google Geocoding when `GOOGLE_PLACES_KEY` is set and falls back to this endpoint when Google fails or has no result; without either it shows `GPS point <lat>, <lng>`. Landmarks live in `backend/src/modules/geo.ts` (`MEKNES_PLACES`), shared with `/v1/geo/search`. | Drivers need a readable pickup, not coordinates; Google Geocoding costs money per call and needs a key (B5); Nominatim's public server forbids app traffic and self-hosting it is heavy, while OSRM already holds the OSM street names. |
| D57 | "I've arrived" only at the pickup (REA P1 #4) | `POST /v1/rides/:id/arrived` refuses with `422 TOO_FAR_FROM_PICKUP` when the driver's last fix younger than 2 min is more than `cancel_rules.arrive_max_distance_m` (default 250 m; 0 turns it off) from the pickup. No fresh fix (GPS lost, tunnel) → allowed, and the `arrived` event stores `distance_m: null` so admins can review; otherwise the event stores the distance. The driver app sends its latest fix just before the call so a fix held back by the location throttle doesn't cause a false refusal, and shows the distance in the error. | "Arrived" starts the rider's wait clock and unlocks the free "rider didn't come" cancel (D12); pressing it from far away is the easiest no-show abuse, made worse by cash. 250 m covers GPS drift in the medina; blocking on a lost fix would strand honest drivers. |
| D58 | Off-app rides (REA P1 #5) | The rider's cancel-reason sheet always shows a warning: never cancel to pay the driver outside the app. Picking "the driver asked me to cancel" opens one more dialog explaining what is lost off-app (trip log, shared trip, SOS to our team) with **Keep the ride in the app** as the main button. If the rider still cancels with `driver_asked`, the server flags the ride and opens a `dispute` report marked `off_app_suspected` for the operators. The cancel still counts for the rider as before. | Cash makes "cancel and pay me directly" easy and leaves the rider unprotected and the platform blind. Counting stays unchanged so the reason can't be used to dodge the rider warning; the report lets operators spot drivers who do it repeatedly. |
| D59 | "Search again" after the driver cancels (REA P1 #2) | When the driver cancels an accepted ride (live, or found on restore within 24 h, D50), Home shows a dialog: **Search again (NN DH)** sends the same pickup, destination and the rider's own offered fare in one tap; **Edit request** leaves the rider on Home with the same details filled in. The phone-verification gate still applies. No backend change: it is a normal `POST /v1/rides`. | Losing a driver is the moment riders give up; one tap keeps them in the flow. The rider's own offer (not the driver's counter) is reused so the rider never pays more without choosing it. |
| D60 | Search in waves (REA P1 #1) | A request first reaches drivers within 40 % of `search_radius_km`, then 70 % at 40 s, then 100 % at 90 s. A city can set its own waves in `cancel_rules.search_waves` ([{after_s, radius_km}], sorted, capped at `search_radius_km`, growing radii only, trimmed to the request lifetime). Each later wave is a BullMQ delayed job (`ride-wave`) that re-checks the ride with a conditional update; the 30 s sweeper catches up lost jobs, jumping to the wave that is due. `ride_notified_drivers` makes sure a driver is notified once per ride; `GET /v1/driver/requests` uses the ride's current radius. The rider sees `Ride.search` {wave, radius_m, drivers_notified}: a stage line ("drivers near you see your request" / "widening the search" / "search widened to X km") until the first offer. Wave settings live in `cancel_rules` (it already holds ride rules such as max bids and PIN attempts) so no admin form change was needed. | Sending every request to a 5 km circle at once makes far drivers bid first and arrive late, and spams them; closest-first keeps pickups short. Widening keeps the fill rate when supply is thin (launch weeks). Telling the rider what is happening reduces cancels during the wait. |
| D61 | Rider moves the pickup once (REA P1 #3) | `POST /v1/rides/:id/pickup` after acceptance: once per ride (`rides.pickup_edited_at`), within `cancel_rules.pickup_edit_max_m` (300 m) of the first point, refused when the ride is no longer `accepted` or the driver's fresh fix is within `pickup_edit_lock_m` (150 m) of the pickup. The price does not change. The driver gets the new point by `ride:update`, a push and a snack bar ("new pickup point: …"). The rider app shows **Change pickup point** on the driver card only while `can_edit_pickup` is true and reuses the address search (with "use my location"). Event `pickup_changed` keeps both points. | GPS pickups are often a street off (medina, big buildings); moving the pin a little saves a phone call and a cancel. One edit, a small circle and the lock near arrival stop abuse (making the driver chase) and keep the agreed price fair. |
| D62 | Driver "Ready to drive" checklist (REA P1 #6) | A driver-app screen (menu **Ready to drive check**, and a red home banner when something is wrong) lists every phone setting that can hide requests, in two groups. **To receive requests:** location service on, airplane mode off, notifications allowed, the "new ride requests" channel on. **To keep working in the background:** location "all the time", battery optimisation off, background activity allowed, battery saver off, Do Not Disturb off. Each failing line has **Fix**, which opens the matching Android settings page (the app's own pages; we still never request `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`), and the list re-checks when the driver comes back. Brand-specific auto-start / pop-up settings can't be read by any API, so the screen links to the battery guide. Native channel `ma.ridema/readiness` (driver only); unknown or non-Android states never count as problems. The home banner leaves out notifications and the location service, which already have their own banner and card. | Missed requests on Xiaomi / Tecno / Infinix phones are the first driver complaint in this market, and the fixes are scattered across settings; one checklist with direct links makes them a two-minute job. |
| D63 | Trust badges on the driver card (REA P2 #15) | Riders see **Documents checked by RideMA** with a tick for **Identity** (CIN front + back, licence, selfie) and **Car papers** (carte grise, insurance, visite technique) on the accepted-ride card, and a one-line version on each offer.
